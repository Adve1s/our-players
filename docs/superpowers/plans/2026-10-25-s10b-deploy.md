# S10b — Deploy the backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the API image, production config, staleness endpoint, rate limit, compose/Caddy files, deploy script and `docs/DEPLOY.md` are ready, so the owner can stand the backend up on the Linode from checklists.

**Architecture:** one Docker Compose project on the host (Caddy → API with in-process scheduler → Postgres 17). The image is built on the owner's machine (podman or docker) and streamed over ssh. The app gains `/health/data` (a pure staleness rule over `games` and `job_runs`) and an optional in-memory per-IP rate limit on `/v1/*`.

**Tech Stack:** Node 24 + tsx, Hono, Drizzle (node-postgres in production), Vitest, Docker/podman, Docker Compose, Caddy 2, Postgres 17, bash.

**Spec:** `docs/superpowers/specs/2026-10-25-s10b-deploy.md` (read it first; it has the reasons). Contract: `docs/SESSIONS.md` §S10b.

## Global Constraints

**Out of scope:** Android builds (S11a, S11b), web go-live (S14b).

**Acceptance criteria**
1. Probe output from the production host shows both APIs reachable (pasted by you).
2. `https://<api>/health` OK; `/v1/meta` fresh; after a few hours, `job_runs` shows scheduled runs.
3. No secrets in git (the reviewer checks); the server refuses to start in production without `CORS_ORIGINS`.
4. The rebuild from `docs/DEPLOY.md` performed once on the host (migrations, `roster`, the season-to-date `backfill`, then `season-stats`), with request count and duration recorded in DEPLOY.md.
5. `docs/DEPLOY.md` covers deploy, rollback, rebuild and secret rotation from zero; the reviewer walks through it against the repo.
6. A production access-log line for a `/v1/days` request shows no query string (pasted).
7. A forced staleness or failure makes `/health/data` return 503 and the monitor emails you (you confirm), while `/health` stays 200.
8. `/v1/days/{date}` p95 is under 150 ms server-side against a DB holding a full season — last season backfilled, locally or on the host (VISION §12; print the measurement and the row counts).
9. Lines arrive within ~15 minutes of a game going final (VISION §2): for one night's games, `boxscore_fetched_at` minus the start of the last `results` run that still saw the game not final is at most 15 minutes (show the query).
10. Requests over the rate limit get 429.
11. `pnpm verify` green.

Project rules that bind every task:
- Criteria 1, 2, 4, 6, 7 (email), 9 and the host side of 10 are **owner steps**, run after the final review from DEPLOY.md checklists. No task runs anything on the real host.
- No new runtime dependency. The only `package.json` change: `tsx` moves from `devDependencies` to `dependencies` in `apps/server` (same version).
- No secrets in git: real values exist only in the host's `/opt/our-players/.env`. The repo gets `deploy/.env.example` with placeholders.
- Error format `{ "error": { "code", "message" } }`. Logs never contain query strings or user preferences.
- Scripts must work on Arch and Ubuntu (no macOS-only flags). On this machine `docker` has no socket permission; use `podman` (and `docker-compose` through `podman compose`).
- Look up Hono, Caddy, Docker Compose and Postgres image specifics with context7 before writing code against them.
- `pnpm verify` green before every commit; Conventional Commits; commit message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. A deploy sends SIGTERM while a scheduled job runs: the HTTP server closes first, the job finishes within compose's 2 min grace period, and the PGlite/pool closes last. Checked in Task 4's local smoke run (`stop` on the api container logs "stopping scheduler" and exits 0).
2. `X-Forwarded-For` with several entries (a client sending its own header through Caddy): the limiter keys on the **last** entry, so a spoofed first entry can't dodge the limit. Test in Task 3.
3. `/health/data` with the database down answers 503 `UNAVAILABLE` and doesn't throw. Test in Task 2.
4. Staleness edges: a game exactly 4 h or 48 h after its start, a `POSTPONED` game, fewer than 3 results runs. Tests in Task 2.
5. Production with `CORS_ORIGINS` set to only whitespace or commas counts as unset and refuses to start. Test in Task 1. Also: the 429 carries CORS headers, so the web app can read it (Task 3).

### Task 3: Per-IP rate limit on `/v1/*`

**Files:**
- Create: `apps/server/src/api/rate-limit.ts`
- Modify: `apps/server/src/api/app.ts` (`ApiDeps` gains `rateLimitPerMinute?: number`; `app.use('/v1/*', rateLimit(...))` **after** the CORS middleware, only when set)
- Test: `apps/server/test/api-rate-limit.test.ts`

**Interfaces:**
- Produces: `export function rateLimit(opts: { limit: number; windowMs: number; now: () => Date }): MiddlewareHandler`. `ApiDeps.rateLimitPerMinute` absent means no limit (tests, `latency`, screenshots keep working with a fixed clock). Task 4's `main.ts` passes `120`.
- Behaviour: fixed windows `Math.floor(now / windowMs)`. One `Map<string, number>` is replaced when the window index changes. Key = the last comma-separated entry of `X-Forwarded-For`, trimmed; if absent, `getConnInfo(c).remote.address` from `@hono/node-server/conninfo` (try/catch; it throws under `app.request`); else `'unknown'`. Request number `limit + 1` and later in the window get 429 `{ error: { code: 'RATE_LIMITED', message: 'too many requests, try again in a minute' } }` with header `Retry-After` = whole seconds to the window's end (≥ 1).

- [ ] **Step 1: Write the failing tests** with `createApp` over `createTestDb()` (`/v1/meta` answers on an empty DB), `corsOrigins: ['https://web.example']`, `rateLimitPerMinute: 3`, a mutable clock starting at `2026-10-25T12:00:10Z`:
  - 3 requests with `X-Forwarded-For: 203.0.113.7` → 200; the 4th → 429; body parses with `errorResponseSchema`, `code === 'RATE_LIMITED'`; `Retry-After === '50'`
  - the 429 to a request with `Origin: https://web.example` carries `access-control-allow-origin: https://web.example`
  - a second IP in the same window → 200
  - `X-Forwarded-For: 198.51.100.1, 203.0.113.7` counts toward `203.0.113.7` (already limited → 429)
  - clock moved to `12:01:00Z` (next window) → 200 again
  - `/health` after the limit → 200
  - without `rateLimitPerMinute`, 10 requests from one IP → all 200
- [ ] **Step 2: Run** `pnpm test api-rate-limit` → FAIL (no 429).
- [ ] **Step 3: Implement** `rate-limit.ts` and wire it into `createApp`. One-line comment: the last XFF entry is the one Caddy added; port 3001 isn't published, so it can't be forged.
- [ ] **Step 4: Run** `pnpm test api-rate-limit api-cors` → PASS, then `pnpm verify`.
