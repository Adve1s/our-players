# S06 — API: days, games, meta Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `/health`, `/v1/meta`, `/v1/days/{gameDate}` and `/v1/games/{gameId}`, typed by a zod contract in `packages/shared`, tested over PGlite seeded by the real ingestion jobs.

**Architecture:** `createApp({ db, now, log })` in `apps/server/src/api/` replaces the singleton `src/app.ts`. The day and game responses reuse `loadRecap` + `gameDayRows` (the recap's code), then append the selected leagues' other games and map to the contract. `main.ts` always opens the DB; the scheduler stays optional.

**Tech Stack:** Hono 4.13 (`app.request`, `onError`, `notFound`, `HTTPException` from `hono/http-exception`), zod 4.6 (`z.iso.date()`, `z.iso.datetime()`, `z.discriminatedUnion`, `z.prettifyError`), Drizzle 0.45 on PGlite, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-19-s06-api-days.md` (approved 2026-10-19, including its "Calls I made").

## Global Constraints

From SESSIONS.md §S06, verbatim:

**Out of scope:** players, search, countries, CORS (S07); app.

**Acceptance criteria**
1. Every response in tests parses with the shared contract schema.
2. Filtering behavior: followed country shown; hidden player removed; favorite from another country included; league filter applied to everyone.
3. Ordering and rows: games with shown players first; DNP and "Not in lineup" rows, and no "Not in lineup" row for a player with no current team; prev/next game day.
4. `latestGameDate` with an injected clock: 08:00 in Riga returns the previous US date.
5. Bad parameters → 400 with the error format; logs contain no query strings (test).
6. With S04a/S05 data loaded, `curl "localhost:3001/v1/days/<date>?countries=LVA"` returns that night's lines; 100 sequential requests print their p95, next to the row counts of `games` and `stat_lines` (a smoke check — the real p95 target is measured in production in S10).
7. `pnpm verify` green.

Also:
- No new dependencies. No migration.
- VISION §10: preferences are `leagues=NHL,NBA&countries=LVA&fav=nhl-8478402&hide=nba-1234`, comma-separated, at most 200 per list, invalid → 400.
- Error body: `{ "error": { "code": "...", "message": "..." } }`. Codes: `BAD_REQUEST` 400, `NOT_FOUND` 404, `INTERNAL` 500, `UNAVAILABLE` 503.
- Day and game 200 responses send `Cache-Control: public, max-age=60, stale-while-revalidate=300`.
- Request logs never contain a query string.
- Response schemas are non-strict `z.object` (an old app must parse a response that gained a field); error `code` is `z.string()`.
- `apps/server` never computes nationality or selection itself: `isShown` via `gameDayRows` only.
- Owner steps (AC6's curl + latency run on the owner's DB) are not plan tasks; the controller runs them after the final review.

## Review Focus

1. A schedule-only game (stored by the schedule job, no box score, no period scores) on `/v1/games` → 200, `periodScores: null`, `rows: []`. Pinned in Task 4.
2. The DB failing mid-request → 500 `INTERNAL` in the error format, with a `request failed` log line that has no query string. Pinned in Task 4.
3. A day whose only games are in a deselected league → `games: []`, and prev/next skip that league's days. Pinned in Task 4.
4. Sloppy list values (`countries=LVA,`, `countries=LVA, EST`, `countries=lva`) → an error that names the parameter, never a silent drop. Pinned in Task 1.
5. A well-formed favorite ID that matches no stored player → ignored, 200. Pinned in Task 4.

### Task 4: `/v1/days/:gameDate` and `/v1/games/:gameId`

**Files:**

**Interfaces:**
- Consumes: Task 1 schemas; Task 2 `createApp`/`badRequest`; Task 3 `DayGame`, `byStartTime`, `seedApiDb` and its constants; existing `loadRecap`, `gameDayRows`.
- Produces:
  - `loadDay(db: Db, date: string, prefs: Prefs): Promise<DayResponse>`.
  - `loadGame(db: Db, gameId: string, prefs: Prefs): Promise<GameResponse | null>`, where `null` means an unknown ID.
  - `parseQuery(c)` (in `app.ts`): a parameter given more than once → `badRequest('<name>: given more than once')`. Otherwise `prefsQuerySchema.safeParse(c.req.query())`, and on failure `badRequest(z.prettifyError(error))`.
  - Path params are parsed as objects (`z.object({ gameDate: gameDateSchema })`, `z.object({ gameId: publicIdSchema })`), so the message names them.
- Assembly (`loadDay`), per the spec:
  1. `loadRecap`, keeping only games in `prefs.leagues`.
  2. `gameDayRows`, then the remaining games sorted with `byStartTime` and given empty rows.
  3. Map to the contract. `side` is `'away'` when `row.team.id === game.away.id`. A `line` row maps to `{ kind, stats }`.
  4. prev/next in one query over `games` where `league in prefs.leagues`: `max(game_date) filter (where game_date < d)` and `min(game_date) filter (where game_date > d)`.
- Shared helper in `day.ts`: `dayGames(data, prefs): DayGameResponse[]` is steps 2–3 over every game in `data`, ordered shown-first. `loadDay` drops the deselected leagues' games from `data` before calling it.
- `loadGame`:
  - look up the `gameDate` by public ID (no row → `null`);
  - `loadRecap` that date, then `dayGames(data, prefs)` without the league drop, so a deselected league's game is still found. Its rows are empty, because `isShown` applies the league filter.
  - pick the game by ID and add its `periodScores`.
- Both routes set the cache header on 200.
