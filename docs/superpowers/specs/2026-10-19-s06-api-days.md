# S06 — API: days, games, meta: design

Session S06, branch `s06-api-days`. Spec: `docs/SESSIONS.md` §S06. The Main page and Game page get their read endpoints, typed by a zod contract in `packages/shared`. The day view reuses the recap's `loadRecap` + `gameDayRows`, so the recap and the app can't drift.

## Contract (verbatim from SESSIONS.md §S06)

**Out of scope:** players, search, countries, CORS (S07); app.

**Acceptance criteria**
1. Every response in tests parses with the shared contract schema.
2. Filtering behavior: followed country shown; hidden player removed; favorite from another country included; league filter applied to everyone.
3. Ordering and rows: games with shown players first; DNP and "Not in lineup" rows, and no "Not in lineup" row for a player with no current team; prev/next game day.
4. `latestGameDate` with an injected clock: 08:00 in Riga returns the previous US date.
5. Bad parameters → 400 with the error format; logs contain no query strings (test).
6. With S04a/S05 data loaded, `curl "localhost:3001/v1/days/<date>?countries=LVA"` returns that night's lines; 100 sequential requests print their p95, next to the row counts of `games` and `stat_lines` (a smoke check — the real p95 target is measured in production in S10).
7. `pnpm verify` green.

No new dependencies. No migration.

## Contract schemas (`packages/shared/src/contract/`, exported from the package index)

Response schemas are plain `z.object` (unknown keys stripped), not strict. Apps on the Play Store lag the server, so an old app must still parse a response that gained a field. The stat payloads reuse the shared schemas' `.shape` in non-strict objects for the same reason.

```ts
// params.ts
const MAX_LIST = 200; // VISION §10: at most 200 IDs per list (also caps countries)
const csv = (item) => z.string().transform(s => s === '' ? [] : s.split(',')).pipe(z.array(item).max(MAX_LIST));
export const prefsQuerySchema = z.object({
  leagues:   csv(leagueSchema) + .min(1), default: every league   // "at least one must stay on"
  countries: csv(countryCodeSchema), default []                   // upper-case alpha-3 only
  fav:       csv(publicIdSchema), default []
  hide:      csv(publicIdSchema), default []
}).transform(q => Prefs)                                          // the Sets selection.ts takes
export const gameDateSchema = z.iso.date();                       // rejects 2026-02-30 and 20260316
// game IDs reuse publicIdSchema

// responses.ts
errorResponseSchema = { error: { code: string, message: string } }   // codes: BAD_REQUEST, NOT_FOUND, INTERNAL, UNAVAILABLE
healthResponseSchema = { ok: true, lastSuccess: Record<jobName, isoDatetime> }
metaResponseSchema = {
  leagues: [{ league, currentSeason: string | null, latestGameDate: isoDate | null }],  // one entry per league, NHL then NBA
  dataUpdatedAt: isoDatetime | null,
}
teamScore = { abbrev: string, score: int | null }
gameSummary = { id: publicId, league, seasonType, gameDate, startTimeUtc: isoDatetime, status, endedIn: endedIn | null,
                away: teamScore, home: teamScore }
playerRef = { id: publicId, firstName, lastName, nationality: countryCode | null }
line = discriminatedUnion('kind', [
  { kind: 'hockey_skater', stats }, { kind: 'hockey_goalie', stats }, { kind: 'basketball_player', stats } ])
playerRow = discriminatedUnion('type', [
  { type: 'line',          side: 'away' | 'home', player: playerRef, line },
  { type: 'dnp',           side, player, reason: string | null },   // ESPN's reason verbatim (S09 decides case)
  { type: 'not-in-lineup', side, player } ])
dayGame = gameSummary + { rows: playerRow[] }                       // rows already in §4.1 order
dayResponseSchema  = { gameDate, prevGameDate: isoDate | null, nextGameDate: isoDate | null, games: dayGame[] }
gameResponseSchema = dayGame + { periodScores: { period, away, home }[] | null }   // null: schedule-only game
```

`side` instead of a team object: the game already carries both teams.

## Routes (`apps/server/src/api/`)

`src/app.ts` moves to `src/api/app.ts` as `createApp({ db, now, log })`, so tests inject the DB, the clock and the log sink.

| Route | Answers |
|---|---|
| `GET /health` | `select 1`, then the latest `finished_at` of a `succeeded` run per job name → 200. A DB error → 503 `UNAVAILABLE`. Staleness never fails it. |
| `GET /v1/meta` | Per league: `currentSeason(db, league, now)` (existing) and `latestGameDate` = `max(game_date)` where `start_time_utc <= now` and `playedOrPlaying` (the scheduler's "started" rule, in SQL). `dataUpdatedAt` = latest `finished_at` of a `results` run that `succeeded` or was `partial`, any league (when we last checked results). |
| `GET /v1/days/:gameDate?<prefs>` | Day response. `Cache-Control: public, max-age=60, stale-while-revalidate=300`. |
| `GET /v1/games/:gameId?<prefs>` | Game response, same cache header. Unknown ID → 404 `NOT_FOUND`. |

Middleware and errors:
- A request-log middleware writes one JSON line per request through the existing `createLogger`: `{ msg: 'request', method, path, status, ms }`. `path` is `c.req.path`, which has no query string.
- `app.onError`: an `HTTPException` (thrown by the param parsing) becomes its status with the error format. Anything else is logged as `{ msg: 'request failed', method, path, error }` and answered with 500 `INTERNAL` and a generic message.
- `app.notFound` → 404 `NOT_FOUND`.
- `main.ts` now always opens and migrates the DB and serves `createApp(...)`. The scheduler stays behind `SCHEDULER_ENABLED=1`.

## Preferences parsing

A small `parseQuery(c, schema)` runs `prefsQuerySchema.safeParse(c.req.query())`. A failure throws `HTTPException(400)` with zod's prettified message, which names the bad parameter. The same goes for the date and ID path params. Rules:
- Every list is comma-separated, with at most 200 items.
- `leagues` defaults to every league, and `leagues=` (empty) → 400.
- Country codes must be upper-case codes from `COUNTRY_CODES`. A malformed public ID → 400.
- A well-formed ID that we don't know is ignored (§3 case 5): it simply matches no player.
- A parameter given twice (`?countries=LVA&countries=EST`) → 400, so a client bug can't silently drop a value (checked with `c.req.queries()`).
- Unknown parameters are ignored, so cache-busters still work.

## Day assembly

1. Parse the date and prefs.
2. `loadRecap(db, date)` (existing): the day's games, all their stat lines, and the players with a line or whose current team plays that day. `DayGame` gains `seasonType`, `gameDate` and `periodScores` (three more selected columns). Games are then filtered to the selected leagues: a deselected league's games don't appear, not even under "Other games".
3. `gameDayRows(day, prefs)` (existing) applies the selection rule (`isShown`) and returns the games with shown rows, by start time. Rows are ordered away team first, then points descending, then goalies, DNP and not-in-lineup. That includes the DNP rows, "Not in lineup" (a FINAL game with a stored box score, the player's current team plays, he has no line in any game that day), and no row for a player with no current team.
4. The remaining games of the selected leagues follow, sorted by the same start-time comparator (exported from `game-day-rows.ts`). One `games` array, so the app splits it on `rows.length`.
5. Map to the contract. `side` = whether the row's team is the game's away or home team.
6. prev/next: one query, `max(game_date) filter (where game_date < d)` and `min(game_date) filter (where game_date > d)` over games in the selected leagues (the `(league, game_date)` index).

A date with no games → 200 with `games: []` and its prev/next.

The game endpoint looks up the game's `gameDate` by public ID (404 if none) and runs the same assembly for that day. Loading the whole day keeps the rule "he played for another team that day" correct. It then returns that one game, plus `periodScores`. A game in a deselected league is still returned, but with no rows.

## Test harness

`apps/server/test/api-seed.ts` builds one PGlite per test file by running the real jobs (`runJob` with `fakeClient` over recorded fixtures), the way `recap.test.ts` already does:
- NHL `roster` (calendar filtered to CBJ, FLA, PIT).
- NHL `results` for 2026-01-17 (CBJ @ PIT, Merzlikins and Silovs), 2026-03-16 and 2026-03-24, each score filtered to the games we hold box scores for.
- NBA `results` for 2026-03-16 (401810839, Porziņģis) and 2026-03-23 (401810899, Leons DNP "COACH'S DECISION"). The other games on those scoreboards are stored without box scores, which gives "Other games".

Two edge players go in with `upsertPlayers`, as `recap.test.ts` does: Girgensons on CBJ's roster (not in lineup), and an LVA player with no current team. The API never writes, so the tests share the seeded DB read-only. Each test calls `createApp({ db, now, log })` and goes through `app.request()`. A helper `get(path, schema)` asserts the status and parses the body with the contract schema, so AC1 holds by construction.

The exact fixture filtering and expected values are settled in the plan by reading the fixtures.

## Latency smoke check (AC6)

`pnpm latency --date YYYY-MM-DD [--countries LVA]` (`apps/server/scripts/latency.ts`) does four things:
- opens the dev DB;
- prints the row counts of `games` and `stat_lines`;
- runs 100 sequential `app.request('/v1/days/…')` calls in-process;
- prints p50, p95 and max.

In-process measures the server-side time VISION §12 targets, and it avoids the PGlite one-process lock that would stop a second process from counting rows while the server runs.
