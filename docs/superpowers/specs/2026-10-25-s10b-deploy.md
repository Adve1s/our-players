# S10b — Deploy the backend — design

Spec: `docs/SESSIONS.md` §S10b. Host: Linode Nanode 1 GB, Frankfurt, Ubuntu 24.04, Docker Compose with API + Postgres + Caddy (D-054). Goal: the API and scheduler run there with Postgres, an alert reaches the owner when data goes stale, and `docs/DEPLOY.md` is good enough to rebuild from zero.

## Contract (quoted from §S10b)

**Out of scope:** Android builds (S11a, S11b), web go-live (S14b).

**Acceptance criteria**
1. Probe output from the production host shows both APIs reachable (pasted by you).
2. `https://<api>/health` OK; `/v1/meta` fresh; after a few hours, `job_runs` shows scheduled runs.
3. No secrets in git (the reviewer checks); the server refuses to start in production without `CORS_ORIGINS`.
4. The rebuild from `docs/DEPLOY.md` performed once on the host (migrations, `roster`, the season-to-date `backfill`, then `season-stats`), with request count and duration recorded in DEPLOY.md.
5. `docs/DEPLOY.md` covers deploy, rollback, rebuild and secret rotation from zero; the reviewer walks through it against the repo.
6. A production access-log line for a `/v1/days` request shows no query string (pasted).
7. A forced staleness or failure makes `/health/data` return 503 and the monitor emails you (you confirm), while `/health` stays 200.
8. `/v1/days/{date}` p95 is under 150 ms server-side against a DB holding a full season — last season backfilled, locally or on the host (VISION §12; print the measurement and the row counts).
9. Lines arrive within ~15 minutes of a game going final (VISION §2): for one night's games, `boxscore_fetched_at` minus the start of the last `results` run that still saw the game not final is at most 15 minutes (show the query).
10. Requests over the rate limit get 429.
11. `pnpm verify` green.

## How it runs in production

```
internet ──443/80──▶ caddy (TLS, Let's Encrypt) ──▶ api:3001 (Hono + scheduler, tsx) ──▶ db:5432 (postgres:17)
                     only these ports published      not published                       not published, volume pgdata
```

Everything lives in `/opt/our-players` on the host: `compose.yaml` and `Caddyfile` (copied from the repo's `deploy/` by the deploy script) and `.env` (secrets, only on the host).

### Image (repo: `Dockerfile`, `.dockerignore`)

Multi-stage, `node:24-slim` (VISION platform; the Node version CI pins in `.tool-versions`):
1. **deps:** `corepack enable`, copy the workspace manifests (`package.json`s of root, `apps/server`, `apps/mobile`, `packages/shared`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`), `pnpm install --frozen-lockfile --prod --filter @our-players/server...`. The mobile manifest is copied only so the frozen lockfile matches; its dependencies aren't installed.
2. **runtime:** `node:24-slim` with `/app/node_modules`, `packages/shared`, and `apps/server`'s `src/`, `scripts/`, `drizzle/`, `data/`, `package.json`. `NODE_ENV=production`, `PATH` gains `/app/node_modules/.bin`, runs as the `node` user, `WORKDIR /app/apps/server`, `CMD ["tsx", "src/main.ts"]`.

The server keeps running on tsx: the source imports without file extensions, so Node's own type stripping can't load it. **`tsx` moves from devDependencies to dependencies in `apps/server`** (no new package). Tests, fixtures and the mobile app aren't in the image. `scripts/` is, so jobs and the probe run inside the container (`docker compose run --rm api tsx scripts/job.ts …`).

### Building and shipping the image: from the owner's machine, no registry (Claude's call)

`deploy/deploy.sh <ssh-target>` (repo, bash, works on Arch and Ubuntu):
1. Refuses a dirty tree (the tag must be a real commit). The tag is `git rev-parse --short HEAD`.
2. Builds `our-players-api:<tag>` with `docker` or `podman` (whichever works), streams it to the host with `docker save | gzip | ssh <target> 'gunzip | docker load'`, and copies `deploy/compose.yaml` and `deploy/Caddyfile` with `scp`.
3. On the host: sets `API_TAG=<tag>` in `.env` and runs `docker compose up -d`, then prints `docker compose ps` and `curl -fsS https://$API_HOST/health`.
4. `--ship-only` stops after step 2 plus the `API_TAG` line: the first-time setup needs the image on the host for the probe and the rebuild before anything starts.

The image name is `localhost/our-players-api:<tag>` everywhere (script and compose). Podman prefixes local images with `localhost/` and Docker accepts that name, so the build works with either tool. On the owner's machine `docker` currently has no socket permission, so podman is what runs.

Why not a registry built by CI (GHCR): a `workflow_dispatch` workflow only runs once it's on `main`, so the first deploy (before this PR merges) would need the local path anyway; GHCR packages also start private (a console toggle or a token on the box). One path is less to document. This also meets S10a's "build images off the box". Deploys happen from `main` after this session. The script warns when the branch isn't `main` but doesn't refuse, because this session's first deploy is from `s10b-deploy`.

**Rollback:** the old images stay on the host. Set `API_TAG=<previous tag>` in `.env` and `docker compose up -d`. Migrations only move forward. DEPLOY.md says so: rolling back past a migration works only if the migration only added things (all of ours so far do); otherwise do the rebuild.

### `deploy/compose.yaml`

- `db`: `postgres:17` (the Debian image is built with ICU, which `collate "und-x-icu"` in search needs), `POSTGRES_USER/DB=our_players`, `POSTGRES_PASSWORD` from `.env`, named volume `pgdata`, healthcheck `pg_isready`.
- `api`: `image: our-players-api:${API_TAG}`, env `DATABASE_URL=postgres://our_players:${POSTGRES_PASSWORD}@db:5432/our_players`, `CORS_ORIGINS`, `SCHEDULER_ENABLED: ${SCHEDULER_ENABLED:-1}` (so `.env` can switch it off, criterion 7), `CONTACT_URL` (optional), `depends_on: db (service_healthy)`, healthcheck `node -e "fetch('http://localhost:3001/health')…"` (no curl in slim), `stop_grace_period: 2m` (a running job tick can finish on a deploy).
- `caddy`: `caddy:2`, ports `80`, `443`, `443/udp`, `API_HOST` from `.env`, volumes `caddy_data` (certificates) and `caddy_config`.
- All: `restart: unless-stopped`; **log retention:** `logging: json-file, max-size 10m, max-file 5` per service (≤ 50 MB each). Docker's default keeps container logs forever.

### Runtime config (repo: `config.ts`, `main.ts`, `db/client.ts`)

- **`NODE_ENV=production` requires `CORS_ORIGINS` and `DATABASE_URL`.** `loadConfig` throws, naming the variable, so the container exits and `docker compose ps` shows it restarting. Without `NODE_ENV=production` the defaults stay as they are (`http://localhost:8081`, local PGlite). The image sets `NODE_ENV`. `DATABASE_URL` is required too because without it a container would quietly write a PGlite database inside itself and lose it on the next deploy.
- `CORS_ORIGINS` = the S14a web origin `https://our-players.<cloudflare-subdomain>.workers.dev` (worker name from `apps/mobile/wrangler.jsonc`; the owner reads the subdomain in the Cloudflare dashboard). S14b checks it against the live site.
- **Migrations** run where they already do: `main.ts` migrates on every start, so a deploy that brings a new migration applies it before the API listens. Job scripts also migrate first (unchanged).
- **Scheduler:** `SCHEDULER_ENABLED=1` in the compose file, so it runs inside the API process as in dev (D-045).
- **`main.ts` hardening, from the parking lot:** load config, `package.json` and overrides before `openDb()`; register the signal handlers right after opening; keep `serve()`'s server and `close()` it first on shutdown. `openPostgres` adds a `pool.on('error', …)` listener that logs instead of crashing, and drops its `shortcut:` once the deploy has run it.
- No secrets in git: `deploy/.env.example` lists `API_HOST`, `POSTGRES_PASSWORD`, `CORS_ORIGINS`, `API_TAG`, `SCHEDULER_ENABLED`, `CONTACT_URL` with placeholders. The existing `.gitignore` `.env` pattern already covers `deploy/.env`.
- The production check lives in `loadConfig`, which `scripts/job.ts` and `scripts/probe.ts` also call. So on the host every script runs through `docker compose run --rm api …`, which passes the full `.env`. A bare `docker run` of the image refuses to start, which is intended.

### Access logs without query strings

- **The app's request log** already logs `c.req.path` (no query) with method, status and ms. It goes to stdout, then to Docker's rotated log, and serves as the production access log for criterion 6: `docker compose logs api | grep '/v1/days'`.
- **Caddy writes no access log**: Caddy only logs requests when a `log` directive is present, and ours has none. No IP addresses are logged anywhere either, which keeps S11b's Data safety answers simple.
- **Caddy's error logs** (e.g. "upstream unreachable" while the API restarts) include the request URI. A global `log default { format filter { request>uri regexp … } }` in the Caddyfile strips everything from `?` on. The builder checks the exact filter syntax in the Caddy docs and proves it with a local container run: a request with `?countries=LVA` to a stopped upstream logs no `countries`.

### Health and the staleness rule

`/health` is unchanged: 200 when the DB answers, 503 when it doesn't, never about upstream. The compose healthcheck uses it.

New **`GET /health/data`** (not under `/v1`, so no CORS or rate limit). It returns 503 `{ "error": { "code": "STALE", "message": "<reasons, joined with '; '>" } }` if any of these holds, else 200 `{ "ok": true }` (Claude's proposal for the thresholds):

1. **Lines late:** a game that started 4–48 h ago is not yet `FINAL` with a box score (status `SCHEDULED`, `LIVE`, or `FINAL` without `boxscore_fetched_at`; `POSTPONED`/`CANCELLED` don't count). Why 4 h: an NHL game with a shootout or an NBA game with overtime is over in about 3 h, and lines are due 15 min after the final, so 4 h is late. The 48 h cap means one game stuck upstream alerts for two days and then stops. This rule also catches a dead scheduler: nothing moves the games along.
2. **Results failing:** the last 3 finished `results` runs of a league all ended `failed` or `partial`. `results` catches each upstream error per day and per game (`run.fail()`), so a run with upstream completely down ends `partial`, not `failed`; only a DB error makes it `failed`. `results` runs every 10 min only while games are on, so this means about 30 min of trouble, and only during the season. A single box score that keeps failing for 30 min also alerts, which is right: its lines aren't arriving.
3. **Schedule stale:** the last `schedule` run that succeeded or was partial is older than 50 h. Without a schedule there are no games, so rules 1 and 2 would stay quiet. 50 h allows one failed 09:00 run (it retries the next day) and alerts after the second. This rule applies year-round; the job runs daily even off-season.

"During the season" comes from the data: off-season there are no started games and no `results` runs, so rules 1 and 2 can't fire. A pure function decides from the rows, with tests for every rule and edge (4 h boundary, 48 h cap, postponed, partial vs failed, both leagues, 50 h). A thin query layer loads the rows. The message names game IDs and job names only; nothing about users is involved.

**Uptime monitor (console, owner):** UptimeRobot free plan (50 monitors, 5-minute checks, email alerts; personal non-commercial use fits this project). Two HTTP(s) monitors: `https://<api>/health/data` and `https://<api>/health`, both alerting to the owner's email. The second tells "host down" apart from "data stale". Fallback if UptimeRobot's terms don't fit: Better Stack's free tier.

**Criterion 7, forcing it (simulates a dead scheduler):** (a) set `SCHEDULER_ENABLED=0` in `.env` and `docker compose up -d api`; (b) pick a game from last night and make it look unfetched again: `update games set boxscore_fetched_at = null where public_id = '<id>'` (`docker compose exec db psql …`). Rule 1 fires: `/health/data` → 503, `/health` stays 200, and the monitor emails within ~5–10 min. (c) Set `SCHEDULER_ENABLED=1` and `up -d api` again: the startup catch-up re-fetches that box score (idempotent), and `/health/data` → 200. Nothing is lost: the row is fetched again. Late October has games every night, so a game from 4–48 h ago always exists. DEPLOY.md keeps the exact commands under "Checks"; the builder runs the same steps against the dev DB first.

### Rate limit (in the app)

Caddy has no rate limiting without a custom build (an xcaddy plugin), so it goes in the app: a Hono middleware on `/v1/*`, a fixed 60 s window, **120 requests per IP per minute**. That's far above one person tapping through days (an app open is 2–4 requests). The 121st request gets 429 `{ "error": { "code": "RATE_LIMITED", "message": "too many requests, try again in a minute" } }` with `Retry-After` (seconds left in the window). State is a `Map<ip, count>` that empties when the window rolls over (bounded memory, no timers), clocked by `ApiDeps.now`, so tests are deterministic.

**Client IP:** the last entry of `X-Forwarded-For`. Caddy's `reverse_proxy` sets that header to the connecting client's address, and port 3001 isn't published, so nobody can reach the API without going through Caddy. The builder confirms Caddy's behaviour in its docs. Without the header (dev, tests) the key is the socket address from `getConnInfo`, or `'unknown'`. `/health*` isn't limited, so the monitor and healthcheck never trip it. Tests: 120 OK then 429 with the error body and `Retry-After`; a new window resets; two IPs counted separately; `/health` unaffected.

### The probe on the production host (criterion 1)

From the built image, before the first `up`: `docker compose run --rm --no-deps api tsx scripts/probe.ts`. The probe needs no fixtures at run time (its IDs are in the code), so the image is enough. No repo change is needed.

### The rebuild (D-021, criterion 4)

DEPLOY.md "Rebuild from scratch", run with the API stopped, so no scheduler competes. The job lock is per process (`runner.ts` `shortcut:`), and this avoids needing a cross-process lock. The first time, it follows `deploy.sh --ship-only` and the probe, so the volume is empty. A later recovery starts with `docker compose down -v`, which deletes the `pgdata` volume. DEPLOY.md warns about this; D-021 says nothing in it is lost for good.
1. `docker compose up -d db`.
2. `docker compose run --rm api tsx scripts/job.ts roster --league nhl`, then `--league nba` (each job migrates first).
3. `… backfill --league nhl --from <season start> --to <yesterday>`, the same for nba (season starts from `docs/sources/`).
4. `… season-stats --league nhl`, `--league nba`.
5. `docker compose up -d`.
6. Totals: a `job_runs` query summing `counts->>'requests'` and the time from first start to last finish, pasted by the owner and recorded in DEPLOY.md.

Preseason note (parking lot, PR #14): a rebuild before the regular season starts stores no stats for the season that just ended. In late October this doesn't apply, but DEPLOY.md says so. Also checked once on real Postgres: one `/v1/players/search?q=…` request (ICU collation).

Running a single job by hand while the API runs (e.g. re-fetching one day) is safe enough: jobs are idempotent upserts, and the worst case is duplicate upstream requests. DEPLOY.md recommends `docker compose stop api` for anything long.

### Latency, criterion 8 (Claude, locally)

The local dev DB holds only this season plus one March night (checked: 95 + 68 games this season). Claude backfills the 2025-26 regular season and playoffs for both leagues into the dev PGlite, in the background during the build (live upstream calls from the owner's machine, ~3,000 requests per league at 1/s, roughly an hour each). Then `pnpm latency` on a busy night, printing the row counts (games, stat lines, players). PGlite is slower than Postgres, so a pass locally is conservative. If it misses 150 ms, the parked fix (`loadDay` prev/next query in parallel) applies, and the measurement repeats on the host.

### Lines within 15 minutes, criterion 9 (owner runs the query)

`final_at` is set by the `results` run that first sees a game `FINAL`. So "the last run that still saw the game not final" is the latest run of that league that started before the run that set `final_at`. The query, for one game day:

```sql
with r as (select started_at, args->>'league' as league from job_runs where job = 'results')
select g.public_id, g.final_at, g.boxscore_fetched_at,
       g.boxscore_fetched_at - (select max(r.started_at) from r
         where r.league = g.league::text
           and r.started_at < (select max(r2.started_at) from r r2 where r2.league = g.league::text and r2.started_at <= g.final_at)
       ) as delay
from games g where g.game_date = :day and g.status = 'FINAL' order by delay desc;
```

The builder checks the column names against `schema.ts` and runs the query on the dev DB, then DEPLOY.md keeps it under "Checks". The owner runs it on the host the morning after a game night the scheduler handled live and pastes the output; every `delay` ≤ 15 min passes. `backfill` also sets `final_at` (to the time of the backfill), so the query means nothing for rebuilt nights.

## Calls made in design (Claude's)

Local build + `ssh` instead of a registry, image named `localhost/…` for podman; rule 2 counts `partial` runs as failing (the reviewer showed an upstream outage ends `partial`); tsx as a runtime dependency; `DATABASE_URL` required in production too; no Caddy access log (the app's request log is the access log, and no IPs are logged); the staleness thresholds (4 h / 48 h / 3 failed runs / 50 h); 120 requests per minute per IP, in the app; the rebuild with the API stopped instead of a cross-process job lock; criterion 8 measured locally on PGlite; Postgres 17; log rotation at 10 MB × 5; one compose project with its own Caddy (if later apps share the box, Caddy moves into a shared project, which is out of scope now).

**Skipped from the parking lot:** `createJobContext()` (a refactor with no deploy effect); the probe checking schemas (the probe only shows reachability, which criterion 1 asks for); the CDN purge note (the API has no CDN: Caddy serves it directly, so `s-maxage` is unused).

**Builder's calls:** file layout inside `deploy/`; the exact Caddy filter syntax; the healthcheck command; the way upstream is made to fail for criterion 7; DEPLOY.md wording.
