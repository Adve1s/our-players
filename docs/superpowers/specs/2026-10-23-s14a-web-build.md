# S14a — Web build as a home-screen app (local) — design

Spec: `docs/SESSIONS.md` §S14a. Goal: the web version is finished and checked locally; S14b only switches it on.

## Contract (quoted from §S14a)

**Out of scope:** going online (S14b); production `CORS_ORIGINS` (S10b).

**Acceptance criteria**
1. The static build is produced by one command and screenshot-checked.
2. Served locally as a production build: deep links work on reload; the manifest and icons load (show them).
3. Hosting choice recorded; the deploy config is ready for S14b and doesn't run on a push to `main`.
4. `pnpm verify` green.

## Hosting (owner: Cloudflare)

Compared in chat: GitHub Pages (no new account, but a `/our-players` sub-path via Expo's experimental `baseUrl` and deep links answered by a `404.html` copy), Cloudflare (new account and an API token, root path, real fallback), Caddy on the Linode (no new account, but an SSH key to production in CI and the site down with the box). **Owner chose Cloudflare**: more sites will follow and should live in one place.

Claude's call within that: **Workers static assets** (an assets-only Worker, no Worker code) rather than classic Pages. Cloudflare points new projects there; Pages stays supported but gets no new features. Both are free for static files and live in the same dashboard. Differences for us: the URL is `our-players.<account-subdomain>.workers.dev` (Pages: `our-players.pages.dev`), and a custom domain needs that domain's DNS on Cloudflare (Pages could CNAME a subdomain from elsewhere) — fine for an own domain bought later; the deSEC name stays the API's. Recorded as D-056.

- `apps/mobile/wrangler.jsonc`: `name: "our-players"`, `compatibility_date`, `assets: { directory: "./dist", not_found_handling: "single-page-application" }`. That setting answers any path that isn't a file with `index.html` and 200, so deep links survive a reload.
- Default Cloudflare cache headers (revalidate every load; the JS bundle names are hashed) — no `_headers` file.

## The build: one command

- `pnpm build:web` (root) → `@our-players/mobile` `build:web` = `expo export -p web` → `apps/mobile/dist/` (git-ignored by `dist/`).
- **API URL:** `EXPO_PUBLIC_API_URL` is inlined at build time, as today; unset → `http://localhost:3001` (`apiBaseUrl`, unchanged). The deploy workflow takes it from the repository variable `WEB_API_URL` (not a secret: it ends up in the public bundle) and fails before building when it's empty, so a deploy can never ship the localhost default.
- `pnpm screenshots` keeps its own export into `.screenshots/web` (same `expo export -p web`, plus its API URL); its shots are of that build.

## Manifest, icons, iOS tags

`apps/mobile/public/` is copied into `dist/` by the export:

- `index.html` (from `expo customize public/index.html`, Expo's template plus): `<link rel="manifest" href="/manifest.json">`; `<link rel="apple-touch-icon" href="/apple-touch-icon.png">`; `apple-mobile-web-app-capable` and `mobile-web-app-capable` = `yes`; `apple-mobile-web-app-title` = `Our Players`; `apple-mobile-web-app-status-bar-style` = `default` (content never sits under the iPhone status bar; `black-translucent` would need safe-area work nobody can check without an iPhone); `theme-color` per scheme (light `#FFFFFF`, dark `#1E1E20` = the header's `surface`); a dark `body` background under `prefers-color-scheme: dark` so a dark launch doesn't flash white; `lang="en"`.
- `manifest.json`: `name`/`short_name` `Our Players`, `start_url` `/`, `scope` `/`, `display` `standalone`, `theme_color` `#FFFFFF`, `background_color` `#F2F2F5` (light only: the manifest has one value), icons 192 and 512 (`any`) and 512 (`maskable`, its own file).
- **Icon (Claude's call, owner can redirect):** a text icon — bold white "OP" on a charcoal diagonal gradient (`#3A3D45` → `#0B0C0E`). After the phone check the owner turned down the first draft's accent blue, tried an orange → pink-red sunrise and a night sky with a rising sun, and chose neutral colors for v1, since the app itself is grey/white (a connected icon-and-app color scheme is a v2 topic), full-bleed square. Android crops a maskable icon to its middle 2/3 and zooms in, so the phone check showed the letters far bigger than in the plain icon: `icons.ts` renders a separate `public/icon-maskable-512.png` with the letters scaled to 0.72 (owner's pick on the phone), and the manifest's `maskable` entry points at it. Source `apps/mobile/assets/icon.svg`; `apps/mobile/scripts/icons.ts` renders it with Playwright (already a dev dependency, no new package) to `public/icon-192.png`, `public/icon-512.png`, `public/apple-touch-icon.png` (180, opaque), `assets/images/favicon.png` (48) and `assets/images/icon.png` (1024, the source S11a reuses for Android). The script checks each PNG's size from its header after writing. PNGs are committed; the script reruns only when the art changes. Android adaptive icon and splash stay S11a's.

## "Add to Home Screen" help page

An app route `src/app/install.tsx` (`/install`, Stack title "Add to Home Screen"), static text in `Card`s with theme tokens: iPhone/iPad (Safari → Share → Add to Home Screen → Add), Android (Chrome → ⋮ → Add to home screen / Install app), computer (Chrome/Edge install icon in the address bar, or a bookmark), and a note that countries and favorites are saved in this browser only, so a home-screen app may start with the defaults. Nothing links to it yet: S14b makes it reachable from the site. Screenshots: light and dark.

## Local production serve

- The screenshot script's static server (`serveWeb`, index.html fallback, refuses paths outside the export) moves to `apps/mobile/scripts/web-server.ts` with `dir`, `port`, `host` parameters; `screenshots.ts` imports it. `.webmanifest` isn't used, `.json` is already typed.
- `pnpm serve:web` → `scripts/serve-web.ts`: serves `dist/` on `0.0.0.0:8090` and prints the local and LAN URLs.
- Test `apps/mobile/test/web-server.test.ts` (a temp dir export): a file comes back with its type; `/player/nhl-1` → `index.html`, 200; `/../package.json` → `index.html`, not the file.
- Evidence for criterion 2: `curl` of `/manifest.json`, the icons and a deep link against `serve:web`, plus a Playwright check in `pnpm screenshots` that the page's manifest and apple-touch-icon links resolve with 200 and `image/png`.

**Phone check (owner, Android over the LAN):** `CORS_ORIGINS=http://<lan-ip>:8090 pnpm dev:server`; `EXPO_PUBLIC_API_URL=http://<lan-ip>:3001 pnpm build:web && pnpm serve:web`; open `http://<lan-ip>:8090` on the phone. Over plain HTTP, Chrome offers only a browser shortcut, not a standalone install (that needs HTTPS — S14b). If the phone can't connect, the laptop firewall needs ports 8090 and 3001 open on the LAN.

## Deploy workflow (written, off)

`.github/workflows/deploy-web.yml`, `on: workflow_dispatch` only, `permissions: contents: read`, `concurrency: deploy-web`: checkout → Node from `.tool-versions` → `corepack enable` → `pnpm install --frozen-lockfile` → fail if `vars.WEB_API_URL` is empty → `pnpm build:web` → `pnpm dlx wrangler@<exact version> deploy` in `apps/mobile` with `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` from secrets. Wrangler runs through `pnpm dlx` (CI only, nothing added to `package.json`), not `cloudflare/wrangler-action`, which would `pnpm add` it inside the workspace. Checked locally with `wrangler deploy --dry-run` (no account needed).

## What S14b switches on

1. Cloudflare account; an API token from the "Edit Cloudflare Workers" template; repo secrets `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`; repo variable `WEB_API_URL` = the production API's `https://` URL (S10b).
2. `deploy-web.yml` gains `push: branches: [main]` (paths: `apps/mobile/**`, `packages/shared/**`).
3. After the first deploy, the production `CORS_ORIGINS` (S10b) = the `workers.dev` origin; check it accepts that origin and rejects others.
4. A link to `/install` from the site (Settings on web).
5. iPhone check: added to the home screen it opens standalone with the icon.
6. The owner may buy a domain by then and serve the site there instead of `workers.dev` (its DNS on Cloudflare, a Workers custom domain): then the web origin in `CORS_ORIGINS`, the deep-link reload and the home-screen install are re-checked on that address.
