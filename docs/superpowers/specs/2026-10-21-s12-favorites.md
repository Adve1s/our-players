# S12 — Search, favorites, hidden: design

Session S12, branch `s12-favorites`. Spec: `docs/SESSIONS.md` §S12; VISION §3 (selection rule), §4.2 (Settings), §4.3 (search, favorites, hidden); area rules `.claude/rules/mobile.md` and `tests.md`. The Search tab finds any player of the selected leagues; each result can be starred or hidden; Settings lists both with remove and undo; Today follows.

## Contract (verbatim from SESSIONS.md §S12)

**Goal:** find any player and star or hide him.

**In scope:** Search tab (debounced, 2+ characters, `/v1/players/search`); star/hide actions that keep favorites and hidden disjoint; Favorites and Hidden lists in Settings (via `/v1/players?ids=`); undo; the Main page refreshes when preferences change.

**Out of scope:** §S12 lists none. Carried from neighbouring sessions: the player page and its favorite/hide actions, pressable rows and cards (S13); anything team-based (v2); offline persistence of server data (Revisit for v2).

**Acceptance criteria**
1. Pure tests for preference actions: favoriting unhides; hiding unfavorites; toggles are idempotent; `version` preserved.
2. On a device: search "porzingis" → star → he appears on Main for a day he played, even with no countries followed.
3. Hiding a Latvian removes him from Main; unhiding brings him back.
4. Screenshots reviewed: results, empty search, both lists.
5. `pnpm verify` green.

## Owner decisions (brainstorming, 2026-10-21)
- **A deselected league is gone everywhere:** Search queries only the selected leagues, and the Settings lists show only players of selected leagues (more leagues will come; showing all would clutter every page). A favorite of a deselected league stays stored and comes back with its league.
- **Preferences stay off the page URL.** They live in device storage and travel only in the API request's query string, which request logs omit (VISION §10). Lists load through `?ids=` (query string), so the S07 path-logging question waits for S13's player page.
- Everything else is Claude's call (owner: "I'll let you make your own decisions on everything").

## Preference actions (`apps/mobile/src/state/prefs.ts`)

```ts
export type Mark = 'favorite' | 'hidden' | null;
export function markOf(p: StoredPrefs, id: PublicId): Mark;               // 'hidden' wins if both (only possible from tampered storage)
export function setMark(p: StoredPrefs, id: PublicId, mark: Mark): StoredPrefs;
export function toggleFavorite(p: StoredPrefs, id: PublicId): StoredPrefs; // favorite ↔ none; a hidden player becomes a favorite
export function toggleHidden(p: StoredPrefs, id: PublicId): StoredPrefs;   // hidden ↔ none; a favorite becomes hidden
```

- `setMark` removes the ID from both lists and adds it to the one `mark` names (sorted, like countries), so favorites and hidden stay disjoint. Setting the mark a player already has returns **the same object** (idempotent; zustand skips the re-render).
- Adding to a list that already has `MAX_LIST` (200) IDs returns the same object: the API rejects a longer list, which would turn every Today request into a 400. My call; with no message in the UI (`shortcut:` comment — nobody stars 200 players; a caption if anyone ever does).
- Undo is `setMark(p, id, previousMark)`.
- The store (`prefs-store.ts`) gains `toggleFavorite`, `toggleHidden`, `setMark`; `version: 1` and `partialize` unchanged.
- `restorePrefs` now drops only invalid favorite/hidden IDs instead of resetting everything (PROGRESS note from S08). The S08 test row "gives the defaults for a malformed favorite ID" becomes "drops only the malformed favorite ID" — an intended behaviour change, not a weakened test. Leagues and countries keep the reset-on-invalid behaviour.

**Tests** (`apps/mobile/test/prefs.test.ts`, test-writer, red first): favoriting a hidden player unhides him; hiding a favorite unfavorites him; `setMark` twice equals once and returns the same object; `toggleFavorite`/`toggleHidden` twice restore the original lists; lists stay sorted and disjoint; the 200 cap for both lists; inputs aren't mutated; `markOf` for each case; `restorePrefs` drops a malformed favorite or hidden ID and keeps the rest. **`version` preserved** (`apps/mobile/test/prefs-store.test.ts`): run store actions over an in-memory `window.localStorage` (the storage edge; AsyncStorage's web build reads it) and check the persisted JSON still carries `"version":1` and the new lists.

## Pure helpers (`apps/mobile/src/lib/players.ts`, tested in `test/players.test.ts`)
- `searchTerm(raw: string): string | null` — trimmed; `null` under 2 characters (then no request).
- `playerMeta(p: PlayerSummary): string` — `NBA · BOS · C · LVA`; no team → `No team`; no nationality → the code is left out.
- `listRows(players: PlayerSummary[], leagues: League[], removed: ReadonlySet<PublicId>): { player; removed: boolean }[]` — only selected leagues; sorted by last name, then first name (`localeCompare`), so a row keeps its place after Remove/Undo; IDs the server didn't return are simply absent (VISION §3.5).

## Queries (`src/api/queries.ts`)
- `useSearch(term, leagues)` — key `['search', term, leagues]`, `enabled: term !== null`, `placeholderData: keepPreviousData` (results don't blank between keystrokes).
- `usePlayers(ids)` — key `['players', ids]` (ids sorted), `enabled: ids.length > 0`, `keepPreviousData`. One query per list, each ≤ 200 IDs.

## Search screen (`src/app/search.tsx`)
Top: a search field ("Search players", same look as Settings' country search, extracted to `components/search-field.tsx` and used by both). Input is debounced 300 ms (a small `useDebounced` in the screen; no dependency).

Below, one surface card:
- under 2 characters: caption "Type at least 2 letters of a player's name."
- loading: spinner; offline (paused): "You're offline. Search works when you're back online."; error: `ErrorState` with Try again.
- no results: `No player matches "xyz".`
- results (≤ 20, server order): one `PlayerItem` per player, divided like the country rows.

`PlayerItem` (`components/player-item.tsx`): name on line one (body, semibold), `playerMeta` caption on line two; on the right two 48 px targets — **★/☆** (accent when starred) and **Hide/Hidden** (accent when hidden). Both are `accessibilityRole="checkbox"` with `aria-checked` and labels "Favorite Kristaps Porziņģis" / "Hide Kristaps Porziņģis". Tapping again reverses, so Search has no separate undo.

## Settings lists (`src/app/settings.tsx`)
Two new cards between Countries and About: **Favorites** and **Hidden**, `aside` = shown count.
- Each row is `PlayerItem` with one text button **Remove** instead of ★/Hide.
- **Undo:** Remove takes the player out of the preferences at once (Today follows), but the row stays in place, dimmed, its button reading **Undo**; Undo puts the old mark back. The screen keeps `removed: Map<PublicId, Mark>` in state and clears it on blur (`useFocusEffect` cleanup), so leaving Settings makes removals final. The list's query IDs are the list ∪ its removed IDs, so a removal doesn't refetch.
- Empty: "No favorites yet. Star players in Search." / "Nobody hidden. Hidden players never show on Today." Loading: spinner; offline: "You're offline. Your players load when you're back online."; error: `ErrorState`.

## How Today reacts
No code: `useDay`'s key already holds `favorites` and `hidden`, so a change makes a new request and the selection rule runs on the server; `keepPreviousData` keeps the old day on screen until the new one is in. `dayMessage`'s "following anything" already counts favorites. Tabs stay mounted, so Today refetches when the store changes, not when you return to it.
