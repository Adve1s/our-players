# Decisions

Lightweight decision records. Append new ones at the end (`/handoff` does this); never rewrite history — supersede instead ("Superseded by D-0xx").

Format: **ID — Title** (date, status) · Decision · Why · Alternatives considered.

---

**D-001 — Monorepo with pnpm workspaces** (2026-10-02, accepted)
`apps/mobile`, `apps/server`, `packages/shared`. Why: one TypeScript contract shared by app and server; one place for Claude to see everything. Alternatives: separate repos (contract drift, more ceremony).

**D-002 — Scheduled ingestion into our own DB; user-agnostic read API** (2026-10-02, accepted)
Jobs fetch by game/league on a schedule; users never trigger upstream calls; the app sends preferences and gets filtered results. Why: politeness to unofficial APIs, resilience to upstream outages, no accounts needed. Alternatives: on-demand proxying (rate-limit and blocking risk, slow).

**D-003 — One adapter per upstream source, mapping to a normalized model** (2026-10-02, accepted)
Why: both sources are unofficial and will change; a breakage should mean fixing one adapter.

**D-004 — PostgreSQL everywhere: PGlite for local dev and tests, real Postgres in production** (2026-10-02, accepted — changes the brief's "SQLite in dev")
Why: "SQLite in dev, Postgres in prod" means two dialects. Drizzle needs separate schema definitions per dialect (`sqliteTable` vs `pgTable`); Prisma pins one provider per schema with provider-specific migrations. Behavior also differs where this app cares (case-insensitive search, JSON columns, dates, booleans), so tests on SQLite wouldn't prove production behavior. PGlite is Postgres compiled to WASM that runs in-process: no install, no Docker, real Postgres semantics, and Drizzle supports it (`drizzle-orm/pglite`). Alternatives: SQLite everywhere including production (viable for one small server, but the brief wants Postgres when deployed); Docker Postgres locally (heavier setup).

**D-005 — Drizzle ORM + drizzle-kit migrations** (2026-10-02, accepted)
Why: TypeScript-first, SQL-shaped (easy to learn and review), supports PGlite and node-postgres with the same `pg-core` schema. Alternatives: Prisma (heavier toolchain, less SQL-visible), Kysely (query builder only; we'd hand-write more).

**D-006 — Hono for the HTTP API** (2026-10-02, accepted)
Why: small API surface similar to ASP.NET minimal APIs; `app.request()` makes API tests trivial without a running server; first-class zod validation. Alternatives: Fastify (equally fine, more concepts), Express (dated typing story).

**D-007 — Vitest for all tests; mobile UI verified with screenshots** (2026-10-02, accepted)
Why: one fast runner for shared + server; UI logic that matters lives in pure modules; screens are checked by a Playwright screenshot script on the web build plus manual phone checks, which gives Claude a visual way to verify its UI work. Alternatives: jest-expo component tests (slower, low value for this app in v1).

**D-008 — Biome for formatting and linting** (2026-10-02, accepted)
Why: one fast tool and one config for the whole monorepo; fast enough to run on every edit via a hook. Alternatives: ESLint + Prettier (two tools, more config).

**D-009 — Nationality = sporting nationality: one alpha-3 code per player; birth country by default; overrides by player ID in a JSON file** (2026-10-02, accepted)
Nationality means the national team a player represents. Each player has one code (or none) with its source, `birth` or `override`. Overrides live in `apps/server/data/nationality-overrides.json`, keyed by public player ID; the first two are Embiid (born CMR → USA) and Towns (born USA → DOM). Why: a player represents one national team, so one value matches the definition and keeps the schema and selection rule simple; the NHL already returns alpha-3; overrides are rare, human-curated and benefit from git review. Alternatives: a set of nationalities (citizenships — not what the app means), name-based matching for players not yet in a league (dropped until needed; Berrouet can be added by ID if he reaches the NBA), overrides in a DB table (needs an admin UI), alpha-2 codes (conversion needed for the NHL).

**D-010 — Stable public IDs derived from source IDs** (2026-10-02, accepted)
`nhl-<id>`, `nba-<espn id>`, same for games. Why: favorites are stored on devices without accounts; IDs must survive DB rebuilds and re-ingestion. If a source is ever swapped, old public IDs stay primary and new source IDs map through `player_external_ids`.

**D-011 — Game day = the league's schedule date; default view = latest started game day** (2026-10-02, accepted)
Why: in Latvia, "last night's games" happen on the previous US date and finish after midnight local time; using the viewer's local date would split one night of games across two days.

Why: adding a sport or position means adding a `kind` and a zod schema rather than migrating wide nullable tables. Alternatives: one table per kind (more joins and migrations), one wide table (many nulls).

**D-013 — No league/team logos or player photos in v1** (2026-10-02, accepted)

**D-021 — Production recovery is a rebuild, not a backup restore** (2026-10-03, accepted — changes VISION §11 "Postgres with daily backups")
Every row in the database can be fetched again from upstream, and the nationality overrides live in git. So recovery means: provision Postgres, then run migrations, the `roster` job, the season-to-date `backfill` and `season-stats`. `docs/DEPLOY.md` documents this rebuild, with its request count and duration, and S10 performs it once on the host. A provider's free automatic snapshots are welcome but not required. Why: backups only protect data we can't recreate, and here there is none; one tested rebuild beats an untested restore. Alternatives: daily `pg_dump` with restore drills (more moving parts for no data we'd lose).

**D-028 — Polite client: per-hostname spacing measured start to start; `Retry-After` capped at 60 s** (2026-10-17, accepted)
`createPoliteClient` queues requests per hostname (`api.nhle.com` and `api-web.nhle.com` count separately) with ≥ 1 s between request starts; retries 429, 5xx, network errors and timeouts up to 3 times with exponential backoff + jitter (base 1 s); honors `Retry-After` as seconds or HTTP date, but a value over 60 s throws `HttpError` instead of sleeping; no retry on other 4xx; 15 s timeout via `AbortController`. A retry pause holds every request to that host, including ones already queued. `fetch` and jitter are injected; the clock is not — tests drive `Date.now` and `setTimeout` with Vitest fake timers. Why: a job should never block for an hour on one header — the next scheduled run retries; start-to-start spacing keeps the client simple and still ≤ 1 req/s per host. Alternatives: one request in flight per host (stricter, slower when a response is slow); unbounded `Retry-After`.

**D-029 — Fixtures are pretty-printed recorder output; endpoint URLs for recording live in `apps/server/scripts/endpoints.ts`** (2026-10-17, accepted)
The recorder writes the body re-indented with 2 spaces so PR diffs are readable, and the `.meta.json` `bytes` keeps the upstream (decoded) size. The recording endpoint table sits in `scripts/`, not `src/`: S03's adapters own their production URLs. Why: readable diffs when a fixture is re-recorded; size answers (VISION §9 Q8) stay honest. Alternatives: byte-exact bodies (one-line JSON diffs), a shared URL table in `src/` (couples a dev tool to adapters).

**D-030 — Nationality rule stays override → birth country → null; NHL `nationalityCode` not adopted** (2026-10-17, accepted)
`resolveNationality` returns the override if one exists (source `override`, even when it equals the birth country), else the birth country (source `birth`), else `{ nationality: null, source: null }`. The birth country reaches it already as an alpha-3 code or `null`; turning source text into a code is the adapters' job. VISION §7 and CLAUDE.md rule 6 are unchanged. Why: for every Latvian the NHL's `nationalityCode` agrees with the birth country (9/9 in the 2025-26 bios), and overrides already cover the known exceptions; adopting it would add the bios pages to the jobs, a third source value and a column for little gain in v1. Adding it later is backward-compatible (parking lot). Alternatives: override → NHL `nationalityCode` → birth country (more correct for players such as Batherson, born USA, plays for CAN; 3 of 50 on bios page 1); ESPN `citizenship` (often missing, and wrong for Embiid).

**D-031 — zod 4 for every schema; country codes as a literal ISO 3166-1 alpha-3 `z.enum`** (2026-10-17, accepted)
`zod` ^4.6.7 is a runtime dependency of `packages/shared` and `apps/server`. `countries.ts` holds the 249 officially assigned codes copied from Debian iso-codes 4.20.1 as an `as const` array, so `CountryCode` is a literal union (a typo like `'LAV'` fails typecheck) and `countryCodeSchema` rejects unknown codes with "unknown ISO 3166-1 alpha-3 country code". Stat payload schemas and the overrides entries are strict objects (an unknown key is a typo). Why: zod is the project's schema tool (CLAUDE.md); a literal list needs no runtime file or dependency and changes only when ISO does. Alternatives: zod 3 (the transitive Expo copy; older API); a country-code package (a dependency for a 249-item list); `^[A-Z]{3}$` only (accepts `XXX`).

**D-032 — Database clients: PGlite on disk (dev), PGlite in memory (tests), node-postgres with `DATABASE_URL`; our own migrate CLI; leagues seeded in code** (2026-10-17, accepted)
`drizzle-orm` 0.45.4 (latest stable; 1.0 still `rc`), `@electric-sql/pglite` 0.5.10 and `pg` 8.23.1 are runtime dependencies of `apps/server`; `drizzle-kit` 0.31.11 only generates migrations into `apps/server/drizzle/`. Every repository takes `Db = PgDatabase<PgQueryResultHKT>`, which both drivers satisfy. `pnpm db:migrate` is `src/db/cli.ts`, not `drizzle-kit migrate`: one code path for PGlite and Postgres that also seeds the two leagues (`on conflict do nothing`), because migrations are generated and never hand-edited. Fixed value sets are `pgEnum`s built from the shared zod enums, so the DB rejects a value the model doesn't know. Tests clone one migrated in-memory template per file (~0.5 s instead of ~2.8 s per database). Why: D-004/D-005 in practice with one schema and no second migration tool. Alternatives: `drizzle-kit migrate` (needs a PGlite driver config and can't seed), a custom SQL migration for the seed (hand-edited), text columns with check constraints (no link to the shared enums).

**D-033 — Upserts are no-ops on unchanged data; a game's stat lines are written as one set; nationality is computed on write** (2026-10-17, accepted)
Every upsert is `insert … on conflict (natural key) do update … where (cols) is distinct from (excluded cols)`, so a repeat write changes no row, not even `updated_at`, and returns 0 changed rows; bookkeeping timestamps use the database's `now()`. Batches are deduped by natural key (last wins). `upsertStatLines(db, gamePublicId, lines)` replaces the game's set in one transaction after validating every line (payload schema, played/stats pairing, kind vs sport, team in the game), so a corrected box score leaves no stale line; an empty batch is rejected, because a real box score is never empty and an empty one would wipe the game (PR #7 review). `season_stats.fetched_at` follows the same rule: it records when the values were stored, and feed freshness comes from `job_runs`. `upsertPlayers` resolves nationality with the overrides on every write; `recomputeNationalities` re-applies them when the file changes and warns about overrides whose player is missing or whose name differs (compared case- and diacritic-insensitively). Why: CLAUDE.md rule 4 taken literally ("re-running changes nothing"), and no window where a new player lacks a nationality. Alternatives: always bumping `updated_at` (rows differ on every run), upsert-only lines (stale lines after corrections), nationality only in the roster job's recompute.

**D-034 — NHL adapter: mappers parse `unknown` themselves; period scores from `score` goals; summaries in one `limit=-1` request** (2026-10-17, accepted)
Each NHL mapper takes parsed JSON as `unknown`, validates it with a raw zod schema (used fields only) and returns the shared model; a schema failure throws `nhl <endpoint>: invalid payload` with zod's message, a value the mapping tables don't know throws `nhl <endpoint>: game|player <id>: …`. Fetchers in `client.ts` are `client.get` → `JSON.parse` → mapper, with the polite client injected; `index.ts` is the adapter's surface. Period scores are counted from `score`'s `goals[]` per period (labels `1`–`3`, `OT`, `2OT`…, `SO`; a shootout counts 1 for the winner, as right-rail does) — right-rail is not fetched. Skater/goalie summaries are one `limit=-1` request with `gameTypeId` (live probe 2026-10-17: 940/940 and 98/98 rows) and throw when rows < `total`. Team `externalId` is the NHL numeric ID; `name` is the common name. Why: malformed payloads are testable at the mapper (AC3); no extra request per game; summaries without `gameTypeId` mix regular season and playoffs (`nhl.md` Q5). Alternatives: right-rail per game (one more request per final game), `start`/`limit` paging (more requests, unverified), team abbrevs as IDs (change on relocation).

**D-035 — NHL edge rules: TOI 00:00 is a DNP line; non-league game types skipped; unknown birth country is null + warning; `OVER` is LIVE** (2026-10-17, accepted)
A box-score line with TOI `00:00` (a dressed backup goalie) becomes `played: false`, `stats: null`, `dnpReason: null` — the recap shows "DNP" (owner ruling). Game types other than 1/2/3 (All-Star, international) are skipped, not errors. A roster/landing `birthCountry` that isn't an ISO alpha-3 code becomes `null` with a returned warning, so one bad code can't sink a roster. `gameState` `OVER` (community docs; after the horn, before `FINAL`/`OFF`) maps to LIVE so a game is finalized only on FINAL/OFF. A goalie's `savePct` is `null` when he faced no shots (preseason reports 0). Season stats keep source values as given (TOI per game stays a float, rule 5; `.claude/rules/adapters.md` says so); `basis: 'totals'` describes the counting stats, while rates keep rate names. Amended after the PR #8 review: game types other than 1/2/3 are dropped before the strict parse (placeholder teams can't fail the payload); an unknown `gameScheduleState` (SUSP, TBD… documented but unseen) skips only its game, with a warning that `mapScore`/`mapSchedule` return; an unknown `gameState` still throws; `fetchRoster` takes one team (`abbrev` + `externalId`). The stats-REST bios fixtures are exempt from S03's AC1 (no mapper reads them until the D-030 upgrade). Why: what a fan expects to see, and loud-but-local failures. Alternatives: an all-zero played line or no line for backup goalies ("Not in lineup" would be wrong); throwing on unknown game types or countries (one All-Star game or odd code would fail a whole job).

**D-036 — Job runner: in-process overlap lock, one `job_runs` row per run, JSON-line logs; the dev PGlite is locked to one process** (2026-10-18, accepted)
`runJob(ctx, name, job, args)` skips a start while the same job name runs in this process (logged, no row), writes `job_runs` (`succeeded`, `partial` when the job reported unit failures through `run.fail`, `failed` when it threw; counts kept either way, `counts.requests` = the polite client's delta) and never rethrows a job's error. Jobs get an injected `JobContext` (db, client, clock, logger, overrides). Logs are one JSON object per line. `openPglite(dir)` holds a `<dir>.lock` pid file until `close()`; a live holder makes a second open fail with a clear message, a dead pid's lock is taken over; `db:reset` deletes the data dir only while holding it. Why: PGlite has no lock and two processes corrupt it; the scheduler (S04b) runs jobs in one process. Alternatives: Postgres advisory locks (re-entrant on PGlite's single connection, so no in-process protection), a `job_runs` partial unique index (stale rows after a crash need expiry), `pglite-socket` to share the dev DB (new dependency).

**D-037 — Ingestion rules: results/backfill by game day, box scores once, guards in the repositories, team list from `schedule-calendar`** (2026-10-18, accepted)
`results` looks at the game days of started SCHEDULED/LIVE games and of FINAL games without a box score (or `--date`); per day: `score` → teams + games, `final_at` stamped, then each FINAL game without `boxscore_fetched_at` gets its box score once. Box-score players not yet stored are written from their landing page (a landing team that isn't stored → no current team + warning); a failed enrichment writes the stub with no current team; the line is never dropped. `backfill` runs the same day step over a range (score covers future games, so no schedule call). Days, games and players fail one by one (`partial`); a whole bad `score`/`schedule` payload stays one failed day. `upsertGames` never moves a stored FINAL game to another status (the row is skipped, a no-op) and never replaces stored period scores with none (the rest of the row is still written, so a LIVE game can become POSTPONED; amended in PR #9 review), and rejects a league that doesn't fit its source, a team from another league, and home == away; `upsertSeasonStats` rejects a kind outside the player's league. `roster` takes the league's teams from NHL `schedule-calendar` (owner ruling: rosters change in-season, and stored teams can be incomplete), upserts players with overrides, and changes `active`/current team only when every roster came back non-empty; then recomputes nationalities. Why: one guard covers every caller; deactivating needs a complete, non-empty answer. Alternatives: a schedule job that skips past games (every other writer stays unguarded); stored teams as the roster list.

**D-038 — Game-day rows: one pure function decides line / DNP / not in lineup** (2026-10-18, accepted)
`gameDayRows({ games, lines, players }, prefs)` returns, per game with a shown player (`isShown`), rows ordered away team first, skaters by points, goalies, then DNP and "Not in lineup" (games by start time; every tie broken by public ID, so the order is stable). "Not in lineup" = the shown player's current team played this game, it is FINAL and its box score is stored, and he has no line that day (a line in another game means he was traded since); no current team → no row. `pnpm recap` prints it with VISION §4.1's card text; S06's `/v1/days` reuses it (owner ruling: the recap and the app must not differ). Why: the rule exists once. Alternatives: a lines-only recap now and the rule in S06 (two versions to keep in sync).

**D-039 — Current season comes from the stored schedule; season stats cover its started season types for every stored player** (2026-10-18, accepted)
`currentSeason(db, league, now)` (`src/db/games.ts`) is the `season` of the game with the latest `start_time_utc ≤ now` that isn't POSTPONED/CANCELLED; with no started game, the season of the earliest SCHEDULED game after `now`; else `null`. So the summer stays on the finished season (the playoffs were the last started games) and the rollover comes when the first preseason game starts. `season-stats` fetches the skater and goalie summaries (`limit=-1`) for each season type of that season with a started game (none started → no requests, `succeeded`), and keeps rows for players already stored in the league, active or not, stubs included; the rest count as `skipped`. S06's `/v1/meta` reuses `currentSeason`. Why: no calendar to maintain, and the stored schedule already knows when a season begins; a player waived or sent down mid-season still has real totals ("rostered" read as "stored"). Alternatives: a date rule (e.g. "season changes on 1 August": wrong for late or early starts and for lockouts), the NHL's `season` endpoint (one more upstream call and adapter for something the schedule already says), active players only (drops real totals).

**D-040 — Box-score corrections: one re-fetch, ≥ 6 h after the final; a first fetch ≥ 12 h after the start counts as corrected** (2026-10-18, accepted)
After its day loop, `results` re-fetches the box score of each FINAL game with a box score, `corrected_at` null and `final_at ≤ now − 6 h` (`CORRECTION_DELAY_MS`), rewrites its stat lines (`upsertStatLines` replaces the set, so changed numbers update and dropped lines go) and sets `corrected_at`; a failure is a `run.fail` and leaves `corrected_at` null, so the next run retries — but only while `final_at` is within the last 24 h (`RESULTS_WINDOW_MS`), unless the run is a catch-up (`catchUp: true`, passed by the scheduler's startup tick and by every manual `pnpm job results`), so a box score that fails every time stops being re-fetched (amended after PR #10 review). The pass is NHL-only until S05: a non-NHL run fails with `arrives in S05` instead of sending ESPN ids to the NHL endpoint. A game whose box score is first fetched ≥ 12 h after its start (`SETTLED_AFTER_START_MS`) gets `corrected_at` with `boxscore_fetched_at`: regular-season games end within ~3.5 h, so that fetch is already past the correction delay — this covers backfill and catch-up after downtime with no flag (playoff marathons excepted). `backfill` never runs the corrections pass. Why: VISION §6.1's rule (once, ≥ 6 h after final) with one request per game; without the 12 h rule a backfilled game, whose `final_at` is its ingestion time, would be re-fetched once more for nothing. Alternatives: re-fetching every final daily for N days (many more requests), a backfill flag (one more mode to get wrong, and it misses catch-up after downtime).

**D-041 — Scheduler: a pure `decide()` on a 10-minute `setInterval`, daily UTC slots, a 24 h results window; the dev server holds the DB only with `SCHEDULER_ENABLED=1`** (2026-10-18, accepted)
`decide(now, leagues, state)` (`src/scheduler/decide.ts`) is pure; `tick` loads its state (games started in the last 24 h or later, uncorrected finals of any age, and at startup started-but-unfinished games of any age, plus each job's latest `job_runs.started_at`), logs the decisions and runs them in order per league: schedule → results → roster → season-stats (results after schedule, so a stale schedule is healed in the same tick). A rejected `runJob` is logged and the tick goes on; a tick still running when the next is due is skipped (logged). Daily jobs have UTC slots 09:00 (schedule), 10:00 (roster), 11:00 (season-stats) — in Riga they move an hour with daylight saving time, which the owner accepted (2026-10-18): a job is due when `now` is past today's slot and its last run started before it, so it fires at most 10 minutes late, once a day, and right after startup if the server was off at slot time; any run counts whatever its status, so a failing daily job waits for tomorrow instead of re-firing every tick. `schedule` also runs at startup when no future game is stored. `results` runs when a game awaiting results (started SCHEDULED/LIVE, or FINAL without a box score) started within the last 24 h, or when a correction is due for a final within the last 24 h; at startup either trigger reaches games of any age (catch-up after downtime), and the startup tick runs results with `catchUp: true` so its corrections pass reaches them too. Ticks stay startup ticks until one completes, so a failed first tick doesn't lose the catch-up (amended after PR #10 review). The window also bounds the corrections trigger, so a box score that fails forever can't make every tick call upstream. `lastRuns` is keyed by league and job, read from `job_runs.args->>'league'` (no league column, no migration; a run without a known league is ignored), so a daily NHL run doesn't count for the NBA, and `main.ts` runs both leagues (amended in S05). The dev server opens the DB, migrates and starts the scheduler only with `SCHEDULER_ENABLED=1`; a failed open/migrate closes the handle (releasing the PGlite lock) and exits 1; SIGINT/SIGTERM (`process.on` with a guard — `once` would leave the second SIGINT that tsx watch relays to Node's default action, killing the process mid-close and leaving the lock) waits for the running tick, closes the DB and exits — but `pnpm dev:server` runs `tsx watch`, which SIGKILLs the child 5 s after its signal (Ctrl-C or a restart on a file edit), so a longer tick dies mid-job: its `job_runs` row stays `running` and the next start takes over the dead pid's lock (`shortcut:` in `main.ts`; run without watch, or make jobs abortable, if that bites). Why: decisions testable with an injected clock and no timers; a slot rule needs only `job_runs`. No croner (Claude's decision, accepted by the owner): a cron library adds a dependency for three daily times a 10-minute tick already hits. Alternatives: croner or node-cron (a dependency; missed slots during downtime need the same `job_runs` check anyway), a separate scheduler process (a second PGlite opener), retrying failed daily jobs every tick (hammers a failing upstream).

**D-042 — ESPN NBA adapter rules: game day from the request, unknown status or season type skipped, stats by label, DNP reason verbatim, whole minutes, country names via iso-codes** (2026-10-18, accepted)
`sources/espn-nba/` mirrors the NHL adapter (shared `parsePayload`/`lookup` moved to `src/sources/common.ts`; NHL messages unchanged). A scoreboard game's `gameDate` is the `dates=` day requested (no event field carries it), so the NBA `schedule` makes 7 scoreboard requests and stops at the first failure (all or nothing). Season `year` is the end year (`2027` → `"2026-27"`); types `1/2/3` → PRE/REG/POST. Status per VISION §8; an unknown status or season type (play-in, All-Star: unseen) skips that game with a warning, extending D-035. Period labels `Q1…Q4`, `OT`, `2OT`…; `endedIn` OT when there are more than 4 periods. Box-score stats are mapped by `labels` (all 14 required); `didNotPlay` → DNP line with `reason` stored verbatim (`"COACH'S DECISION"`; played rows carry the same text, so it is read only on DNP rows). NBA `minutes` stay whole minutes (VISION §8; `.claude/rules/adapters.md` says so). Positions G/F/C (+ PG/SG/SF/PF); anything else throws. Birth countries go through `countryFromName`: exact match on the iso-codes 4.20.1 `name`/`common_name`/`official_name` table plus ESPN aliases (USA, England/Scotland/Wales, and the live run's Russia, Bosnia & Herzegovina, Democratic Republic of Congo); unknown → null + warning. The `overview` fixture is exempt from S05's AC1 (owner ruling). Why: loud-but-local failures, and the source's own values. Alternatives: game day from the Pacific date of the start time (wrong for Asian preseason games); throwing on an unknown status (one new ESPN status would sink a whole night).

**D-043 — Jobs dispatch through one adapter per league; NBA season stats from bulk `byathlete` within a 20-page budget** (2026-10-18, accepted)
`src/jobs/adapters.ts` gives each league `day`, `week`, `boxscore`, `player`, `teams`, `roster`, `seasonStats`; every job calls `ADAPTERS[args.league]`, and the job algorithms (D-037, D-039, D-040) are unchanged.
